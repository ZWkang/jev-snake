# snake-jev-runner Specification

## Purpose

通过用户指定的 Typesafe 官方 JEV 1.13 做持续移动贪吃蛇的真实方向决策，保持模型请求和游戏循环独立，并将选择、概率、响应时间与是否生效作为可观察记录。

## Requirements

### Requirement: 真实结构化决策

runner SHALL 支持 Typesafe 直连与显式选择的 OpenRouter，不自动回退。接口使用 state/questions/choice 契约，单步模式返回方向，两步模式返回一个有序方向对；系统 MUST 校验结果属于请求定义的选项并保留实际返回模型、原始概率和置信度。第二个方向 SHALL 表示第一个方向实际执行后下一移动的备用选择，不得把两个独立方向选择冒充有条件关系的计划。概率合计不等于 1 SHALL 只作为诊断信息，不阻止提交有效选择，不自动归一化。不得把聊天解析、固定规则或模拟结果标为 JEV。

#### Scenario: 概率合计为 0.99 或 1.01

- **WHEN** 模型返回有效选项，单项概率字段合法但合计为 0.99 或 1.01
- **THEN** 原样保存概率并提交模型选择，记录合计提示，不因此中断对局或替换方向

#### Scenario: 未配置密钥

- **WHEN** 没有当前 provider 对应的 TYPESAFE_API_KEY 或 OPENROUTER_API_KEY
- **THEN** 明确显示未配置，真实 runner 拒绝启动，不创建虚假 JEV 对局

#### Scenario: 一次返回连续方向

- **WHEN** 两步模式下，模型针对实际第 N 步返回“右、下”
- **THEN** 形成同一个真实请求产生的计划，右绑定 N+1，下绑定 N+2，第二步说明以第一步向右执行为前提，不产生第二次模型调用

### Requirement: 当前局面与在途请求

runner SHALL 使用服务端当前已提交的实际局面请求模型，每次最多一个在途请求。单步模式目标固定为紧接着一次移动，不预测多步或填充未来队列。fixed 每个实际 tick 最多询问一次，接纳后等待实际 tick 推进；fixed 两步模式每轮形成当前 tick + 1 的主动作及 tick + 2 的备用动作，后续移动仅为条件预测，不读取或伪造未来随机奖励。已有备用不阻止对新实际局面的请求，在途请求期间由服务端独立推进和选择备用。response 仅使用单步，等前一次应用确认后立即读取新局面并再次询问，不等待定时 tick，也不额外 sleep。response 的 stale_state 或非法反向被拒绝时保持不动，重新读取当前局面后可再次询问同一 tick；请求格式、鉴权、版本或不支持目标错误必须显式失败。返回结果 SHALL 携带原观察、原目标和摘要提交，禁止重绑旧观察或将整个迟到计划截断后重新提交。

#### Scenario: 结果已过时

- **WHEN** 请求返回时单步目标或两步计划的第一步目标 tick 已过，或对应局面摘要失效
- **THEN** 该结果不生效并记录原因；两步计划整体拒绝，第二步不得单独移植，已有旧备用的生命周期不受该拒绝影响；runner 再基于最新实际状态决策，fixed 继续按原规则推进，response 保持不动直到有效动作到达

#### Scenario: 已有备用仍发起新请求

- **WHEN** 计划 A 的第一步在 N+1 生效，A 的第二步已为 N+2 预留
- **THEN** runner 基于 N+1 的实际局面发起计划 B；N+2 到点时不等待 B 返回，服务端按新决策与备用的优先级结算

#### Scenario: 备用消费后的恢复

- **WHEN** A 的备用在 N+2 生效，而 B 随后因第一步目标已过被拒绝
- **THEN** runner 基于最新实际局面请求下一计划，不重试 B 的过期动作，也不把 A 的备用复制到 N+3

#### Scenario: 响应模式的串行闭环

- **WHEN** response 模式已取得一条有效模型结果
- **THEN** 只提交该结果一次，收到 applied 或明确的结果事件后才为新的实际局面请求下一次；不会并发预问或为了动画播放而等待

#### Scenario: 正常等待不是请求失败

- **WHEN** 模型请求仍未结束且对局未停止
- **THEN** runner 保持该请求在途并暴露等待状态或日志，不按旧步长定时取消、不启动并行替代请求、不生成方向

#### Scenario: 奖励变化导致响应失效

- **WHEN** response 请求返回后因奖励到期收到 stale_state
- **THEN** 不移动，也不死等 tick 增长；重新读取当前实际状态再请求，保留本次拒绝事实

### Requirement: 模型结果可追溯

系统 SHALL 保存实际模型版本、选择、概率、置信度、请求耗时及最终接纳/生效结果。两步计划 SHALL 关联一次模型调用和两步各自的生命周期；备用生效不新增调用计数、不伪造本步推理耗时，计划概率不得冒充单步方向概率。失败记录明确原因，不返回假成功，也不切换其他模型。

#### Scenario: API 失败

- **WHEN** 当前服务商返回错误或格式不符合契约
- **THEN** runner 暴露错误，并通过受保护通道标记对局中断；已有备用不把已知 API 错误变成成功，历史保留已提交过程

#### Scenario: 真实错误与终局相邻发生

- **WHEN** 已发生终局，但模型请求抛出真实 HTTP、网络或响应校验错误
- **THEN** 错误仍明确输出并使 runner 非零退出，不将其视为成功或主动取消；只有与实际 abort reason 相同的错误才可归类为终局取消

#### Scenario: 请求在结束前未完成

- **WHEN** 对局结束时模型请求尚未返回
- **THEN** runner 记录请求开始及取消、对应观察步和目标步、实际等待时长，不虚构模型决策或将等待时间标为纯推理耗时

### Requirement: 显式选择和关闭备用模式

runner SHALL 支持 `--decision-mode two_step_fallback` 和 `--decision-mode single_step`，新 fixed runner 调用默认选择 two_step_fallback，并在启动日志和创建配置中明确模式。single_step SHALL 关闭两步生成与备用执行；response 仅使用 single_step，显式请求 response 与 two_step_fallback 的冲突组合必须报错。模式在一局内固定，未携带模式的既有创建客户端与旧记录 SHALL 解释为单步，不能悄悄改变原局。无效模式 SHALL 在创建对局前报错。

#### Scenario: 500ms 两步对局

- **WHEN** 运行 runner 并指定 `--tick-ms 500`，未覆盖 decision-mode
- **THEN** 新局保存 two_step_fallback 模式和 500ms 步长，启动日志明确显示两步备用模式

#### Scenario: 关闭兜底

- **WHEN** 使用 `--decision-mode single_step` 创建新局
- **THEN** 每次模型仅决定下一步，迟到且无已接纳动作时沿原方向移动，既有两步对局不受影响

### Requirement: 响应模式的显式启动配置

runner SHALL 提供显式选择 fixed/response 的启动配置，默认保留 fixed。response 的请求正文明确标注模式及当前观察步/唯一下一步，不声明固定间隔或截止时间；历史保存实际发送的正文。两种模式均使用真实服务商和现有凭证隔离，概率合计偏差仍只作诊断。response 不消费两步备用计划，显式请求不兼容的组合必须报错。

#### Scenario: 启动响应模式

- **WHEN** 用户以 response 模式启动 runner，没有显式固定步长
- **THEN** 创建 response 对局并运行单响应单步循环；用于 fixed 的默认间隔不会变成该局的等待时间

#### Scenario: 明确提供冲突选项

- **WHEN** response 同时显式指定固定步长，或同时显式选择 two_step_fallback
- **THEN** 在创建对局前明确拒绝，不偷偷选一种模式

#### Scenario: 请求失败或用户停止

- **WHEN** API、网络或解析失败，或用户主动停止
- **THEN** 沿用明确错误/停止结算与请求取消记录，不因为响应模式改为假结果、自动换模型或自动继续走

### Requirement: 版本化紧凑动作上下文

runner SHALL 为新单步请求生成 `action-facts-v3`、为新两步请求生成 `two-step-plan-v3`，保留 state/questions/choice 接口和原观察 tick、目标 tick、真实计时语义。模型 SHALL 收到动作后果和必要局面摘要，不再被要求根据完整蛇身坐标进行多层路径推理；单步事实仅出现一次，两步第一步事实共享且第二步条件明确。新格式 SHALL 显式改变 contextVersion，历史缺失版本、v1、v2 保留原解析，新格式缺少必需事实不能伪装成旧格式通过校验。

#### Scenario: 三种运行组合

- **WHEN** 分别创建 fixed 单步、fixed 两步和 response 单步请求
- **THEN** 均使用对应 v3 context，选项和执行协议保持原样；response 仍没有固定截止和第二步计划

#### Scenario: 旧记录及错误版本

- **WHEN** 读取历史无版本/v1/v2 请求，或控制通道收到未知 context 版本、缺少 v3 必需事实的请求
- **THEN** 历史请求保持原文；错误的新请求明确校验失败，不丢字段后冒充已接纳

### Requirement: 明确的模型选择优先级

指令 SHALL 依次要求避免即时碰撞、避免已证实的强制碰撞路线、比较退路和空间，再考虑苹果与星星的收益及到达条件。无已证实危险不等于安全；模型 SHALL 不被要求生成解释、路线或多个独立判断来拼成相关两步计划。静态指标和路线证据的含义 SHALL 与选项说明一致，不伪装为生存概率或强制推荐方向。

#### Scenario: 食物更近但存在确定死路

- **WHEN** 某方向更接近苹果但强制通道已证明必死，另一个方向没有这项证据
- **THEN** 请求明确要求优先避开前者，不让曼哈顿距离或星星收益覆盖生存优先级

### Requirement: 上下文构建成本与原始正文可追溯

runner SHALL 保存实际发出的请求正文，并记录非负的本地 context 构建耗时和 UTF-8 请求字节数；已有 `requestMs` 继续表示模型调用往返，`inputTokens` 仅在服务商真实返回时保存。诊断 SHALL 不含密钥、不把缺失值填为零，不改变概率合计偏差只作提示、API 错误显式失败和单在途请求的既有行为。

#### Scenario: 新请求完成

- **WHEN** v3 请求实际返回并提交
- **THEN** 保存正文与传输正文一致、字节数与其 UTF-8 编码一致，构建与模型耗时分开，可在评估中比较输入成本

#### Scenario: API 报错或概率合计为 0.99

- **WHEN** 请求报 HTTP 错误，或有效返回仅存在概率合计偏差
- **THEN** 前者沿用错误中断，后者原样提交；不因 context 改造增加重试、模型切换或自动选方向

### Requirement: 连续频道复用真实单局运行能力

同一真实单局运行能力 SHALL 同时支持现有 CLI 和服务端频道调用，保留现有 fixed/response、单步/两步配置、原观察与目标绑定、进度事实、模型选择、概率、请求原文和错误语义。每次调用 SHALL 仅控制明确归属的一场局，返回真实结束状态及错误；跨局倒计时属于频道，不改变局内请求节奏。CLI 默认仍只运行一局，不因频道功能自动循环。

#### Scenario: CLI 兼容

- **WHEN** 用户使用既有 `npm run jev -- ...` 参数运行
- **THEN** 仍只创建和控制一局，保留原模式默认值、冲突校验及退出语义

#### Scenario: 频道正常连续两局

- **WHEN** 频道在第一局结束和运行器清理成功后开始第二局
- **THEN** 第二局有新的观察历史、控制凭证和 matchId，第一局的事件、在途请求或动作不能污染第二局

### Requirement: 停止续局与停止模型调用分离

所有者停止后续开局 SHALL 不取消已运行本局的模型请求，不改变其方向或强行结束。只有本局真实终局、既有明确错误或服务退出 SHALL 按既有规则取消请求和清理连接。正常终局同时出现真实 API 错误时 SHALL 保留错误，不把它吞掉并继续下一局。

#### Scenario: 所有者停止时模型还在等待

- **WHEN** 本局正在等待模型响应，所有者停止连续开局
- **THEN** 此请求继续等待，返回后按原目标和规则提交；频道只记住本局结束后不再开局

#### Scenario: 终局与真实 API 错误相邻

- **WHEN** 引擎已终局，但运行器仍报告真实 API、网络或解析错误
- **THEN** 该错误仍使频道进入故障，不被当成成功清理而安排下一局
