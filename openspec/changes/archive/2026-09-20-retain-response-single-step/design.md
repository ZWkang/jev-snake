## Context

动机见 [proposal.md](proposal.md)。这是跨配置、协议、执行、历史恢复和 UI 的能力收敛，需要设计文档。

当前源码证据：

| 位置 | 已观察行为 | 设计影响 |
| --- | --- | --- |
| `server/jev/game-config.ts`、`.env.example` | 默认 fixed/两步，response 才使用单步 | CLI 和频道共用入口必须同步收敛 |
| `shared/snake/schema.ts` | 创建与历史使用 fixed/response 联合配置；单步/计划控制并存 | 新建校验不能直接替代历史解析 |
| `server/matches/service.ts` | `advance` 同时处理奖励到期、固定 tick 和计划备用；response 动作原子移动 | 删除固定移动路径，保留独立奖励到期 |
| `server/jev/runner.ts`、`client.ts` | runner 按协议选择 `askJev`/`askJevPlan`，当前已发 v4 context | 保留现有 v4 单步请求；删实时两步分支 |
| `server/app.ts`、`server/start.ts`、`server/watch/channel.ts` | 能力声明 `[1,2]`，停止流程也按计划模式选择协议 | 停用计划执行时不能破坏旧局清理 |
| `scripts/run-jev.ts`、`server/matches/restore.ts` | 分支配置要求完全等于源局；恢复把 config/recordVersion/rulesVersion 当作全程不变的物理字段 | 仅保留响应单步续跑，不引入跨模式转换 |
| `server/jev/progress.ts` | 历史局面键只看几何、方向和食物，不含推进模式 | 响应分支保留真实历史，不重复计数 |
| `src/features/snake/{Scene,ReplayPage,DecisionInput}.tsx` | 共用新局与历史展示，保留计划及原速度 | 按所查看事件区分当前能力与历史展示 |

主规范仍有 fixed 默认、两步要求及 v3 描述；“明确的模型选择优先级”也落后于当前 v4 的自主决策指令。本 change 的 delta 将相关条文与保留的实际行为对齐，不恢复旧的策略排序。未同步为主规范的历史 change 文件保持原文，不当作新运行能力的依据。

## Goals / Non-Goals

**Goals:**

- 用单一生产运行路径实现“有效响应、原子一步、读取新局面、下一请求”。
- 明确区分可创建/可执行的配置与可读取/可重放的旧记录。
- 每条保留的旧模式分支都有历史读取、精确恢复或取消清理用途，不能重新进入实时固定移动。
- 响应历史分支可检验、可再次恢复，且不改变棋盘生成、RNG、奖励、配色与进度事实。

**Non-Goals:**

- 不调整模型、服务商、方向策略、奖励规则、棋盘布局或 UI 视觉风格。
- 不删除旧数据、重写旧事件、引入自动寻路、并发预问、限步、等待上限或错误兜底。
- 不实现新定时调度框架，不因本次收敛重构无关证据分析算法。

## Decisions

### 1. 新建配置和历史配置分离

共享层保留可读历史的 `GameConfig` 联合；新增或明确命名新建配置 schema/type，唯一结果为 response/single_step/null。`createSchema` 与生产 `gameConfig` 使用新建配置；数据库、历史请求和恢复仍用历史校验。新建省略模式时写入明确值，显式旧模式或数值间隔不被 defaults 吞掉。

CLI 接受 `--step-mode response`、`--decision-mode single_step` 作为兼容的同值声明；拒绝其他模式及任何 `--tick-ms`。`SNAKE_STEP_MODE` 只能省略或为 response，已设置的 `SNAKE_TICK_MS` 输出明确的弃用提示并继续响应单步；删除该环境变量即可停止提示，它不会参与新局计时；fork 仍完整继承原响应配置，不应用新建地图或模式环境值；遗留步长提示仍会输出。错误提供移除/替换配置的提示。`.env.example` 去掉固定步长，仅说明唯一模式；不自动修改真实 `.env` 或接触密钥。

选择保留无歧义的同值参数，避免现有响应单步命令无必要失效。替代方案“只改默认值”不能关闭其他入口；“把旧值静默转成 response”违背显式失败原则；“收窄所有历史类型”会破坏旧数据。

### 2. 服务端只保留单步执行，历史兼容留在读取和清理边界

新控制只执行协议 v1 的 start/action/stop。健康接口 `supportedProtocolVersions` 改为 `[1]`。移除新计划接纳、两步裁决、固定 tick 补跑、迟到沿原方向、未来 pending 移动队列的实际执行路径。

已有请求先按其历史规范解析、计算原有 hash 并查去重；若确有完全相同的已保存请求，返回原回执，冲突则报错；没有既有回执才进入实时协议校验，新的 v2/plan 必须明确拒绝。这不是运行旧协议的后门。创建去重同理：已存在的旧创建标识只返回原记录，未命中的旧配置不允许创建。不能用新的默认模式重算旧请求 hash。

服务启动继续对 running 局记录 server_restart 并取消旧未执行计划。将取消所需的计划状态更新与备用执行解耦，只允许记录 cancelled；手动旧 fixed ready 局可读取或显式 stop，但 start/action 不能运行。关闭服务和频道清理调用明确的终止路径，不用已停用的协议生成新计划命令。旧终局和历史回执不改写。

替代方案“完全删除计划相关类型和取消函数”会丢失历史生命周期；“保留旧执行器作为兼容开关”违背唯一运行方式。

### 3. 区分奖励计时、移动提交与频道倒计时

局内调度器只负责星星到期；无星星无需安排移动 timer。保留服务端单调时钟锚点、到期优先于动作校验、停止时真实时长，以及事务提交失败时不广播部分成功。

有效 action 立即完成一次移动或碰撞，写入原始模型信息、事件、状态及 applied 回执；没有 action 不走。`deadlineInMs`、`nextTickAt` 和固定间隔为 null。不增加最短间隔、额外 sleep、周期性调用或自动续走。频道五秒局间倒计时保留，与局内移动分开。

替代方案“删除所有 timer”会令星星不再按时过期，也会破坏频道续局，不能采用。

### 4. 生产 runner 和上下文只生成单步

`runJevMatch` 只接受响应单步活动局，始终调用 `askJev`；移除 `movedAfter` 固定步等待、协议二分支与 `askJevPlan` 的真实调用入口。提交后 applied 立即下一轮；stale_state/invalid_direction 重新取当前局面，其余失败沿用现有显式中断和请求取消语义。

保留当前 action-facts-v4、positive-v1 见证和 progress-v1 历史，保持四选一与 JEV 自主取舍。旧两步 schema 和展示仍解析原文，不能因为收敛模式退回 README 中的 v3。评估脚本只真实请求 response 单步；历史 fixed/两步比较数据标为离线 fixture，任何仍需要的旧构建辅助移到明确的测试/离线用途，生产 runner 不再引用。

替代方案“只隐藏两步参数但保留生产分派”没有完成简化；“改提示词令模型只返回第一步”仍可能产生不一致的联合概率，不能作为协议迁移。

### 5. 仅保留已有响应单步续跑

用户要求解决提案中过度设计后，本 change 收窄为：仅原 response/single_step 局能续跑；旧 fixed/两步局仍可查看和回放，但新的 fork 明确返回 mode_retired，且不创建新局。已保存的旧分支请求重发只返回既有记录，不新增执行。

响应局沿用当前 restoreMatchAt 与 forked 边界：精确继承配置、布局版本、种子、几何、奖励、RNG、分数、tick、累计时间、上一移动时刻及真实进度，清空旧控制关联。CLI 继续验证源配置完整相等，不再增加转换规则。原记录版本 1/2/3 和 SQLite 版本不变，没有 recordVersion=4。

这是对旧续跑能力的明确收敛，避免为了删除运行模式引入新的混合模式历史体系。

### 6. 展示、测试和文档围绕唯一当前模式

新局展示响应等待、真实间隔和平均步频；固定配置速度和备用面板仅在对应历史事件出现。旧历史按原 event.state 展示，响应续跑仍默认定位 forked 边界。`decisionStatistics` 保留原版本统计，新响应移动不能误算为 coast。

已有 response/runner/HTTP/WS/SQLite 测试作为基础。频道测试目前通过固定时间 `advance` 令蛇死亡，需改为提交真实合法单步动作直到真实终局，测试替身仅控制外部模型返回，不伪造服务端移动成功。旧 fixed/two-step 测试改为停用校验、旧记录读取与取消；保存固定 fixture 以验证历史，不再要求生产服务创建旧模式供测试。

README 改成直接 `npm run jev`、唯一响应行为、废弃配置迁移和响应续跑范围说明；不改旧验收文档的历史结论。

## Risks / Trade-offs

- [旧默认环境] → 遗留 SNAKE_TICK_MS 仅明确提示、不阻断；显式 fixed 配置仍报错并指出应改为 response，不自动改用户环境文件。
- [收窄 schema 破坏已有数据] → 新建、实时控制、历史解析分别校验；混合历史和原始 JSON 回归覆盖三种旧组合。
- [删除 fixed 循环时漏掉星星到期] → 保留奖励 timer，覆盖慢响应、无响应及到期与 action 同时发生。
- [旧模式续跑被停用] → CLI/API 明确告知仅支持响应单步续跑，不创建替代局；原历史仍可回放。
- [取消旧计划时重新开放 v2 控制] → 单独保留终止/只读去重用途，健康接口和新 v2 请求拒绝测试验证不可执行。
- [规范与当前代码漂移] → delta 采用实际 v4、自主选择语义；不按旧主规范实现策略排序或复活两步。
- [影响布局/配色] → 保留当前 layoutVersion/RNG 约束及相关回归。

## Migration Plan

1. 实施先建立新建/历史边界和旧记录 fixture，随后收敛服务执行、runner、频道与分支，再更新展示和文档；所有生产入口一起交付。
2. 部署前停止旧服务写入并备份 SQLite；调整废弃环境配置。正常停服按原规则记录中断，异常退出由新服务启动追加 server_restart；不在线重写正在运行的局。
3. 新服务保留数据库和频道开启意图，按现有恢复规则取消旧运行局；后续频道创建只使用响应单步。配置错误进入故障，用户更正并恢复后继续。
4. 验证新默认入口、旧参数拒绝、奖励计时、两局连续观战、混合历史和响应分支。使用独立测试数据和项目规定的 agent-browser 命名 session，不修改用户已有浏览器状态。
5. 本次不升级数据库或记录版本。回退前停止写入，旧后端仍可读取已有响应记录；不得以恢复备份静默删除部署后历史。
